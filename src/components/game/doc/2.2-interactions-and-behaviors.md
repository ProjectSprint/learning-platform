# 2.2) Interactions and Behaviors (Event-Driven Handling)

The behavior system provides declarative, event-driven handling of user
interactions. Instead of writing useEffect loops over events, question authors
define BehaviorRules that pattern-match on game events and execute handlers.

For exact exported method contracts (side effects, return behavior, and
guardrails), use `3.1-runtime-api-reference.md` as canonical. This document focuses on rule
modeling and authoring patterns.

```typescript
import type {
  BehaviorDefinition,
  BehaviorRule,
  HandlerCtx,
  GuardCtx,
  EventTrigger,
  ScheduledCtx,
} from "@/components/game/engine/runtime";
import { entityClicked, modalSubmitted, terminalInput, whenEntityArrivedAtSpace, whenEntityPlacedInSpace, whenEntityTransferredToSpace, modalClosed, phaseChanged } from "@/components/game/engine/runtime";
```

## BehaviorDefinition

The top-level behavior configuration, attached to `QuestionDefinition.behaviors`.

```typescript
type BehaviorDefinition<TContext> = {
  initialContext: TContext;           // Initial value for question-level context
  rules: BehaviorRule<TContext>[];   // Ordered list of rules (first match wins)
};
```

**TContext** is a question-specific state object for tracking cross-rule state
that doesn't belong in GameState. Common fields:

- `navigateAway: boolean` — Signal for the page to call onQuestionComplete()
- `lastConfiguredDeviceId: string | null` — Track which device was last configured

## BehaviorRule

A single rule: when trigger matches and guard passes, run handler.

```typescript
type BehaviorRule<TContext> = {
  id: string;                                                  // Unique ID for debugging
  on: EventTrigger;                                            // Declarative event pattern
  guard?: (ctx: GuardCtx<TContext>) => boolean;               // Optional filter (return true to allow)
  handler: (ctx: HandlerCtx<TContext>) => void | Promise<void>; // Effect to execute
};
```

**Rule evaluation:** For each event, rules are checked in order. The first rule
whose `on` trigger matches AND whose `guard` returns true (or is absent) wins.
Only one rule executes per event. Remaining rules are skipped.

## EventTrigger

Declarative pattern matchers. Each optional field narrows the match — omitted
fields match anything.

### Trigger Factory Functions

| Function | Matches Event | Parameters |
|----------|--------------|------------|
| `entityClicked(entityType?, space?)` | `ENTITY_CLICKED` | Filter by entity type and/or space ID |
| `whenEntityPlacedInSpace(space?, entityType?)` | `ENTITY_ENTERED_SPACE` | Filter by target space and/or entity type |
| `whenEntityTransferredToSpace(space?, entityType?)` | `ENTITY_MOVED` | Filter by destination space and/or entity type |
| `whenEntityArrivedAtSpace(space?, entityType?)` | `ENTITY_ENTERED_SPACE` or `ENTITY_MOVED` | Unified arrival trigger for either source event |
| `modalSubmitted(modalId?, modalActionId?)` | `MODAL_SUBMITTED` | Filter by modal ID and/or action button ID |
| `modalClosed(modalId?)` | `MODAL_CLOSED` | Filter by modal ID |
| `terminalInput(match?)` | `TERMINAL_INPUT` | Filter by exact string or RegExp |
| `phaseChanged(to?, from?)` | `PHASE_CHANGED` | Filter by target and/or source phase |

### Examples

```typescript
// Match any entity click
entityClicked()

// Match only router clicks
entityClicked("router")

// Match router clicks in the "board" space
entityClicked("router", "board")

// Match any modal with "save" button
modalSubmitted(undefined, "save")

// Match specific modal
modalSubmitted("router-config-abc")

// Match any terminal input
terminalInput()

// Match terminal input matching a regex
terminalInput(/^ping\s+/)

// Match transition to "terminal" phase
phaseChanged("terminal")
```

### Lane Scheduler Helpers

For lane-based flows (single-core/dual-core queues), runtime exposes pure
helpers:

```typescript
import { pickLane, hasFreeLane } from "@/components/game/engine/runtime";
```

- `pickLane(...)` supports `first_free` and `round_robin` policies.
- `hasFreeLane(...)` checks if any enabled lane is currently available.

These helpers keep lane selection deterministic and avoid route-specific
selection logic drift.

### Raw EventTrigger Type

For cases where factory functions don't suffice:

```typescript
type EventTrigger =
  | { event: "ENTITY_PLACED_IN_SPACE"; space?: string; entityType?: string }
  | { event: "ENTITY_TRANSFERRED_TO_SPACE"; space?: string; entityType?: string }
  | { event: "ENTITY_ARRIVED_AT_SPACE"; space?: string; entityType?: string }
  | { event: "ENTITY_LEFT_SPACE"; space?: string; entityType?: string }
  | { event: "ENTITY_CLICKED"; entityType?: string; space?: string }
  | { event: "ENTITY_UPDATED"; entityType?: string }
  | { event: "MODAL_OPENED"; modalId?: string }
  | { event: "MODAL_CLOSED"; modalId?: string }
  | { event: "MODAL_SUBMITTED"; modalId?: string; modalActionId?: string }
  | { event: "TERMINAL_INPUT"; match?: string | RegExp }
  | { event: "PHASE_CHANGED"; from?: string; to?: string }
  | { event: "ENGINE_STARTED" }
  | { event: "ENGINE_FINISHED" };
```

## GuardCtx (Read-Only)

Passed to `guard` functions. All fields are readonly.

```typescript
type GuardCtx<TContext> = {
  readonly event: GameEvent;                // The current event being processed
  readonly provenance: EventProvenance;     // Trace metadata for this event/rule evaluation
  readonly entity: EntityData | undefined;  // Resolved entity (if event has entityId)
  readonly snapshot: GameState;             // Current game state snapshot (stale Redux point-in-time)
  readonly phase: string;                   // Current phase (shortcut for snapshot.phase)
  readonly store: Readonly<TContext>;        // Current behavior store (live in-memory behavior state, read-only)
};
```

### Common Guard Patterns

```typescript
// Only run during terminal phase
guard: ({ phase }) => phase === "terminal",

// Only run when question is not completed
guard: ({ snapshot }) => snapshot.question.status !== "completed",

// Only match specific modal prefix
guard: ({ event }) =>
  event.type === "MODAL_SUBMITTED" && event.modalId.startsWith("router-config-"),

// Combine phase and entity conditions
guard: ({ phase, entity }) =>
  phase === "playing" && entity?.type === "router",
```

## HandlerCtx (Mutable)

Passed to `handler` functions. Provides full read/write access.

```typescript
type HandlerCtx<TContext> = {
  // ── Read-only event info ──
  readonly event: GameEvent;                // Current event
  readonly provenance: EventProvenance;     // Event trace metadata
  readonly entity: EntityData | undefined;  // Resolved entity

  // ── Read-only snapshot ──
  readonly snapshot: GameState;             // Stale Redux point-in-time snapshot
  readonly phase: string;                   // Current phase

  // ── Live behavior store ──
  store: TContext;                           // Live in-memory behavior state (mutable)
  mutate: (updater: (ctx: TContext) => void) => void;  // Immer-style mutation

  // ── Command API (single flat surface for all mutations) ──
  cmd: CommandApi;

  // ── Effect helpers ──
  delay: (ms: number) => Promise<void>;     // Async delay
  once: (key: string, fn: () => void) => void;  // Execute fn only once per key
  schedule: (
    key: string,
    ms: number,
    fn: (ctx: ScheduledCtx<TContext>) => void | Promise<void>,
  ) => void;
  cancelSchedule: (key: string) => void;
};
```

### ScheduledCtx

Callbacks executed through `schedule(...)` receive a scheduled context.
It matches `HandlerCtx` but omits event/entity because it is timer-driven.

```typescript
type ScheduledCtx<TContext> = Omit<
  HandlerCtx<TContext>,
  "event" | "entity"
> & {
  readonly snapshot: GameState;
  readonly phase: string;
};
```

## CQRS Contract: snapshot / cmd / store

The three data-access surfaces on `HandlerCtx` have distinct consistency guarantees:

- **`ctx.snapshot`** — **stale Redux point-in-time.** A read-only `GameState` captured at the start of the current event batch. Calling `ctx.cmd.moveEntity(...)` dispatches to Redux synchronously, but `ctx.snapshot` does **not** update within the same handler. The new state is visible only when the next event fires (after React re-renders and `stateRef.current` is refreshed). Use `snapshot` for guards and reads, but never assume it reflects mutations you just issued.

- **`ctx.cmd`** — **eventual fire-and-forget dispatch.** A flat `CommandApi` surface that wraps all world/interaction/flow/progress mutations. Every `cmd.*` call is a Redux dispatch that queues a state change and appends events to the game event queue. The effects are real but asynchronous from the handler's perspective — the snapshot will catch up on the next event.

- **`ctx.store`** — **live in-memory behavior state.** The `TContext` object owned by the behavior reactor. Mutations via `ctx.mutate(fn)` are applied immediately and synchronously — a second read of `ctx.store.myField` in the same handler returns the updated value. Context changes do NOT trigger React re-renders; the page sees updated store on the next render caused by other state changes.

```typescript
handler: (ctx) => {
  // snapshot is stale — shows pre-mutation world
  const oldCount = ctx.snapshot.entities["req-1"] ? 1 : 0;

  // cmd is fire-and-forget — mutation is queued
  ctx.cmd.destroyEntities(["req-1"]);

  // store is live — mutation is immediate
  ctx.mutate((s) => { s.processedCount += 1; });
  console.log(ctx.store.processedCount); // updated immediately
},
```

### Key HandlerCtx Members

**cmd** — Single flat CommandApi surface. See [3.1-runtime-api-reference.md](./3.1-runtime-api-reference.md).
```typescript
ctx.cmd.patchEntity(entityId, { data: { dhcpEnabled: true } });
ctx.cmd.patchEntityState(entityId, { ip: "192.168.1.10", status: "success" });
ctx.cmd.openModal(buildSuccessModal());
ctx.cmd.closeModal("config-123");
ctx.cmd.setPhase("terminal");
ctx.cmd.completeQuestion();
ctx.cmd.terminal.write("Reply from 192.168.1.10: bytes=32 time<1ms TTL=64");
ctx.cmd.terminal.finish();
```

**mutate** — Mutate the behavior store (Immer-style).
```typescript
ctx.mutate(s => {
  s.navigateAway = true;
});
ctx.mutate(s => {
  s.lastConfiguredDeviceId = deviceId;
});
```

**EntityArray** — Serializable, `structuredClone`-safe generic ordered array
ADT for use inside `mutate` callbacks. Designed to give behavior
stores an atomic, owned queue/stack/set without requiring custom reducer
logic.

```typescript
import {
  createEntityArray,
  arrayPush, arrayPop, arrayShift, arrayUnshift, arrayRemove,
  arrayPeekHead, arrayPeekTail, arraySize, arrayHas, arrayAll,
  type EntityArray,
} from "@/components/game/engine";
```

**Type:** `EntityArray<T = string>` — defaults to `string` (entity IDs).
Use a branded/union type as `T` for stronger type safety:

```typescript
type MyBehaviorContext = {
  pendingRequests: EntityArray;          // EntityArray<string>
  activeLanes: EntityArray<CoreLaneId>;  // branded union
};

initialContext: {
  pendingRequests: createEntityArray(),              // infers EntityArray<string>
  activeLanes: createEntityArray<CoreLaneId>(),
}
```

**Mutating operations** (call inside `mutate`):

| Function | Description |
|---|---|
| `arrayPush(a, item)` | Append to tail (FIFO enqueue) |
| `arrayUnshift(a, item)` | Prepend to head (LIFO push) |
| `arrayShift(a)` | Remove and return head, or `null` |
| `arrayPop(a)` | Remove and return tail, or `null` |
| `arrayRemove(a, item)` | Remove first occurrence of `item` |

**Non-mutating reads** (safe to call anywhere):

| Function | Returns |
|---|---|
| `arrayPeekHead(a)` | First item or `null` |
| `arrayPeekTail(a)` | Last item or `null` |
| `arraySize(a)` | Item count |
| `arrayHas(a, item)` | `true` if `item` is present |
| `arrayAll(a)` | Readonly `T[]` snapshot |

**Cancel-on-pickup pattern** — when dequeuing, cancel any pending removal
timer for that entity. This handles the race where `checkTimeouts` already
fired and scheduled deletion before `pickupFromQueue` ran:

```typescript
let capturedId: string | null = null;
ctx.mutate((s) => { capturedId = arrayShift(s.pendingRequests); });
if (!capturedId) return;

// Stop the timeout-removal timer if checkTimeouts already scheduled it
ctx.cancelSchedule(`cores:timeout-remove-${capturedId}`);
```

**Keep in sync on entity removal:**
```typescript
// When a timeout removes an entity still in the array:
ctx.mutate((s) => {
  arrayRemove(s.pendingRequests, entityId);
});
```

**delay** — Async delay for handler. Makes handler async.
```typescript
handler: async ({ cmd, delay }) => {
  cmd.terminal.write("Processing...");
  await delay(1000);
  cmd.terminal.write("Done!");
}
```

**once** — Execute a function only once per unique key. Useful for
one-time setup effects.
```typescript
once("initial-help", () => {
  cmd.terminal.write("Type 'help' for available commands.");
});
```

**schedule / cancelSchedule** — Keyed timer orchestration owned by runtime.
Scheduling with the same key replaces prior timer. Use this for deterministic
deferred actions without manual `setTimeout` lifecycle handling.
```typescript
schedule("udp:send:frame-1", 1500, (sctx) => {
  sctx.cmd.removeFromSpace("frame-1", "internet");
});

cancelSchedule("udp:send:frame-1");
```

## Event System Internals & Critical Pitfalls

### Which cmd API calls generate which semantic events

Not every `cmd.*` call produces every event type. Knowing the mapping
prevents silent deadlocks where a rule is waiting for an event that will
never fire.

| Command API call | Redux action dispatched | Semantic events generated |
|---|---|---|
| `cmd.placeInSpace(id, spaceId)` | `ENTITY_ADDED` | `ENTITY_ARRIVED_AT_SPACE` |
| `cmd.moveEntity(id, toSpaceId)` | `ENTITY_MOVED` | `ENTITY_ARRIVED_AT_SPACE` via `toSpaceId` (`ENTITY_TRANSFERRED_TO_SPACE` trigger) |
| `cmd.removeFromSpace(id, spaceId)` | `ENTITY_REMOVED` | `ENTITY_LEFT_SPACE` |
| PathSpace animation completes | `ENTITY_REMOVED` (via `onEntityPathComplete`) | `ENTITY_LEFT_SPACE` |
| `cmd.destroyEntities([id])` | `ENTITIES_DELETED` | — |
| `cmd.patchEntity(id, patch)` | `ENTITY_UPDATED` | `ENTITY_UPDATED` |

**Critical asymmetry — arrivals vs departures:**

- `ENTITY_ARRIVED_AT_SPACE` fires for **both** programmatic moves (`cmd.moveEntity`) and
  initial adds (`cmd.placeInSpace`).
- `ENTITY_LEFT_SPACE` fires **only** when an entity is explicitly removed from a space
  (`cmd.removeFromSpace` or PathSpace natural completion). It does **NOT** fire
  when `cmd.moveEntity` is called — the source lane is freed silently.

**Consequence:** if you want to react when a lane is freed by a programmatic move
(e.g., offloading a request to io-wait mid-path), listen on the **destination** space
using `ENTITY_ARRIVED_AT_SPACE`, not on the source lane using `ENTITY_LEFT_SPACE`:

```typescript
// Fires when cmd.moveEntity(requestId, SPACE_IDS.ioWait) is called
BehaviorRule({
  id: "my-rule",
  on: { event: "ENTITY_ARRIVED_AT_SPACE", space: SPACE_IDS.ioWait, entityType: "request" },
  handler: (ctx) => { /* lane is now free */ },
}),

// Does NOT fire for cmd.moveEntity — only for cmd.removeFromSpace / path completion
BehaviorRule({
  id: "my-rule",
  on: { event: "ENTITY_LEFT_SPACE", space: SPACE_IDS.serverLane },
  handler: (ctx) => { /* never called after moveEntity */ },
}),
```

### Snapshot semantics inside handlers

`ctx.snapshot` is a **snapshot** captured at the start of each event. Calling
`ctx.cmd.moveEntity(id, newSpaceId)` dispatches to Redux synchronously, but
`ctx.snapshot` does **not** update within the same handler. The new state is visible
only when the next event is processed (after React re-renders and
`stateRef.current` is refreshed).

```typescript
handler: (ctx) => {
  ctx.cmd.moveEntity(requestId, SPACE_IDS.ioWait);
  // ctx.snapshot still shows requestId in the old lane — stale!
  const laneEntities = getSpaceEntityIds(ctx.snapshot, laneSpaceId); // old snapshot
},
```

**Pattern to work around this:** listen for the resulting `ENTITY_ARRIVED_AT_SPACE`
event in a separate rule. By the time that rule's handler runs, `stateRef.current`
has been updated by React and `ctx.snapshot` is fresh.

### First-match-wins and merged responsibilities

The reactor breaks after the **first** rule whose trigger matches AND guard passes.
If two rules share the same trigger/guard conditions, only the first one ever runs —
the second is effectively dead code.

**Symptom:** you have `rule-A` that calls `pickupFromQueue` and `rule-B` that
deletes the entity, both listening to `ENTITY_LEFT_SPACE` from a lane for requests.
`rule-A` fires, `rule-B` never does → entities are never deleted.

**Fix:** merge both responsibilities into one rule, or ensure the rules use
different guard conditions to partition the event space:

```typescript
// One rule does both
BehaviorRule({
  id: "on-lane-free",
  on: { event: "ENTITY_LEFT_SPACE" },
  guard: ({ event, snapshot }) => isLaneEvent(event, snapshot),
  handler: (ctx) => {
    ctx.cmd.destroyEntities([ctx.event.entityId]); // delete completed request
    pickupFromQueue(ctx);                           // refill the lane
  },
}),

// Two rules with same guard — second never fires
BehaviorRule({ id: "rule-a", on: ..., guard: sameGuard, handler: pickupFromQueue }),
BehaviorRule({ id: "rule-b", on: ..., guard: sameGuard, handler: deleteEntity }), // dead
```

## Side Effects

The behavior reactor (`useBehaviorReactor`) has these side effects:

1. **Event processing** — On each render where `events.length > 0`, the reactor
   iterates all events, matches rules, and executes handlers asynchronously.
2. **Event acknowledgment** — After all events are processed, `ack()` is called
   to advance the engine cursor. This prevents double-processing.
3. **Store mutation** — `mutate()` mutates the store ref directly
   (not via React state). Store changes are visible immediately to subsequent
   rules in the same batch but do NOT trigger re-renders.
4. **Processing guard** — A `processingRef` prevents concurrent processing if
   a new render occurs while handlers are still executing.

## Behavior-Driven Flow (Recommended Architecture)

Use this execution model as your default:

1. UI emits a domain event (`ENTITY_MOVED`, `MODAL_SUBMITTED`, `TERMINAL_INPUT`).
2. Reactor scans rules top-to-bottom.
3. First matching trigger + passing guard executes.
4. Handler mutates through `ctx.cmd` (single flat CommandApi).
5. Runtime emits resulting events and updates state.
6. Reactor calls `ack()` after the batch finishes.

Why this matters:
- Rule ordering is part of behavior design, not an implementation detail.
- "First match wins" means broad fallback rules should be placed last.
- Mutations in page-level `useEffect` and behavior handlers can conflict; keep
  rule decisions in behaviors whenever possible.

### Page vs Behavior Responsibilities

Prefer this split:

- **Page (`-page.tsx`)**
  - Render UI
  - Register drawers/arrows
  - Show/hide terminal
  - Resolve declarative phase rules
  - React to behavior store flags (for example, navigate on completion)
- **Behavior rules**
  - Validate moves/commands
  - Open/close modals
  - Update entity/space state
  - Progress/transition decisions tied to gameplay events

Imperative hooks are still valid for orchestration, but avoid giving them
independent gameplay rule branches that duplicate behavior handlers.

## Complete Example

```typescript
import type { TerminalInputEvent } from "@/components/game/engine/runtime";
import type { BehaviorDefinition, BehaviorRule } from "@/components/game/engine/runtime";
import { entityClicked, modalSubmitted, terminalInput } from "@/components/game/engine/runtime";

type MyBehaviorContext = {
  navigateAway: boolean;
};

const rules: BehaviorRule<MyBehaviorContext>[] = [
  // 1. Handle entity clicks → open config modal
  {
    id: "my.router-click",
    on: entityClicked("router"),
    handler: ({ entity, cmd }) => {
      if (!entity) return;
      cmd.openModal({
        id: `config-${entity.id}`,
        title: "Router Configuration",
        content: [
          { kind: "field", field: { id: "dhcpEnabled", kind: "checkbox", label: "Enable DHCP" } },
          { kind: "field", field: { id: "startIp", kind: "text", label: "Start IP", placeholder: "192.168.1.10" } },
        ],
        actions: [
          { id: "save", label: "Save", variant: "primary", validate: true },
          { id: "cancel", label: "Cancel", closesModal: true },
        ],
      });
    },
  },

  // 2. Handle modal save → update entity data
  {
    id: "my.config-save",
    on: modalSubmitted(undefined, "save"),
    guard: ({ event }) =>
      event.type === "MODAL_SUBMITTED" && event.modalId.startsWith("config-"),
    handler: ({ event, cmd }) => {
      if (event.type !== "MODAL_SUBMITTED") return;
      const entityId = event.modalId.replace("config-", "");
      cmd.patchEntity(entityId, {
        data: {
          dhcpEnabled: !!event.values.dhcpEnabled,
          startIp: String(event.values.startIp ?? ""),
        },
      });
    },
  },

  // 3. Handle terminal commands
  {
    id: "my.terminal-command",
    on: terminalInput(),
    guard: ({ phase }) => phase === "terminal",
    handler: ({ event, snapshot, cmd }) => {
      const input = (event as TerminalInputEvent).input.trim().toLowerCase();
      if (input === "help") {
        cmd.terminal.write("Commands: ping <ip>, help");
        return;
      }
      if (input.startsWith("ping ")) {
        const target = input.split(" ")[1];
        // Validate against entity state...
        cmd.terminal.write(`Reply from ${target}: bytes=32 time<1ms TTL=64`);
        cmd.openModal(buildSuccessModal());
        cmd.terminal.finish();
        cmd.completeQuestion();
        return;
      }
      cmd.terminal.write("Unknown command. Type 'help'.", "error");
    },
  },

  // 4. Handle success modal → navigate away
  {
    id: "my.success-navigate",
    on: modalSubmitted("success", "primary"),
    handler: ({ mutate }) => {
      mutate(s => {
        s.navigateAway = true;
      });
    },
  },
];

export const MY_BEHAVIORS: BehaviorDefinition<MyBehaviorContext> = {
  initialContext: { navigateAway: false },
  rules,
};
```

## Limitations

- **First match wins.** Only one rule executes per event. If you need multiple
  handlers for the same event, combine logic in a single handler.
- **No event re-emission.** Handlers cannot emit new events that trigger other
  rules in the same batch. State changes made via `cmd` APIs will emit events
  consumed in the NEXT batch.
- **Store is ref-based.** Changes via `mutate()` do not trigger React
  re-renders. The page sees updated store on the next render caused by other
  state changes.
- **Async handlers block subsequent events.** If a handler uses `delay()`, the
  next event in the batch waits until the delay completes.
- **Guard type narrowing.** Guards receive `GameEvent` union type. You must
  narrow the type manually (e.g. `event.type === "MODAL_SUBMITTED"`) to access
  event-specific fields.
